# Reactions — ручной чек-лист живой проверки (QA-1)

> Дополняет автоматические тесты (`tests/unit/test_reactions_*`, `tests/unit/test_bot_utils.py`,
> `tests/unit/test_admin_reactions_*`, `tests/integration/test_migration_018_message_reactions.py`,
> `tests/integration/test_alembic_online_upgrade.py`, `tests/unit/test_reactions_allowed_updates.py`).
> Эти пункты требуют реального Telegram-чата и живого бота — их нельзя проверить без сети/API,
> поэтому они не в CI. Источник: `docs/plans/reactions-2026-08-03.md` §5.1/§7, ADR-0004 Decision 5.

Предусловие: как минимум два тестовых чата — один, где бот **администратор**, и один, где бот
**обычный участник** (нужен для проверки "молчаливого" отказа без прав).

## 1. Права администратора (R-D1)

- [ ] В чате, где бот — обычный участник: включить `reactions_enabled` через админ-панель
      (`/adm_react_*`). Ожидается popup-предупреждение "бот не админ" сразу при переключении
      (ADR-0004 Decision 5 — активная проверка при включении, не из кеша).
- [ ] В том же чате открыть меню реакций админ-панели повторно (без действий) — строка статуса
      должна по-прежнему показывать "не администратор" (значит, каждый рендер меню делает живой
      `get_chat_member`, а не читает устаревший кеш).
- [ ] Поставить реакцию человеком на сообщение в этом чате. Ожидается: апдейт `message_reaction`
      **не приходит вообще**, без ошибки в логах (это и есть риск §5.1 — Telegram отправляет
      апдейты о реакциях, только когда бот администратор).
- [ ] Выдать боту права администратора в этом чате. Повторно открыть меню реакций — строка
      статуса должна поменяться на "администратор" без перезапуска бота.
- [ ] В чате, где бот уже администратор: включить `reactions_enabled` — popup-предупреждения быть
      не должно.

## 2. Хранение истории (R-1)

- [ ] В чате-админе поставить реакцию 👍 на сообщение человека. Проверить в БД
      (`SELECT * FROM message_reactions ORDER BY id DESC LIMIT 5`) — появилась строка
      `action='added'`, `reaction_type='emoji'`, `emoji='👍'`, `user_id` = реальный (тестовый) id.
- [ ] Снять реакцию — появилась вторая строка `action='removed'` с тем же эмодзи.
- [ ] Заменить реакцию (поставить другой эмодзи поверх старой, если Telegram-клиент это
      позволяет одним тапом) — должны появиться `removed` для старой и `added` для новой одним
      апдейтом (диф `old_reaction`→`new_reaction`, не два независимых события).
- [ ] Анонимная реакция от имени канала/чата (если тестовый чат — публичная группа с опцией
      анонимного администратора): проверить, что строка легла с `user_id IS NULL` и
      `actor_chat_id` заполнен.
- [ ] Выключить `reactions_history_enabled`, оставив `reactions_enabled` включённым; поставить
      реакцию — новая строка в `message_reactions` не появляется (сверить `count(*)` до/после),
      но остальной модуль (R-5) продолжает работать.
- [ ] Выключить `reactions_enabled` целиком; поставить реакцию — апдейт логируется как
      обработанный (или вообще не порождает эффектов), никаких новых строк.

## 3. Реакция вместо ответа на tier-3 (R-5)

- [ ] Спровоцировать сообщение, которое проходит tier-3 (`llm_judge`) и получает решение "не
      отвечать словами". Ожидается: бот молча ставит реакцию (эмодзи из
      `ALLOWED_REACTION_EMOJI`) вместо текстового ответа, ровно одну.
- [ ] В чате с ограниченным набором `available_reactions` (Settings → Reactions → выбрать
      подмножество эмодзи в тестовой группе) повторить — бот не должен падать; ожидается
      деградация до отсутствия реакции (см. `responder.py`'s `TelegramBadRequest` swallow), без
      трейсбека в логах уровня ERROR.
- [ ] Спот-чек списка `ALLOWED_REACTION_EMOJI` (`src/services/modules/reactions/models.py`) —
      backend-dev пометил его ASSUMED (не проверен живым вызовом). Вручную поставить через бота
      минимум 5 эмодзи из списка, по одному из разных "визуальных семейств" (обычные — 👍🔥❤,
      составные с ZWJ — ❤‍🔥, менее очевидные — 🍾🗿🫡), убедиться что `setMessageReaction`
      принимает все пять без `TelegramBadRequest`.

## 4. Гигиена / regressions

- [ ] `git grep` по `tests/` на реальные Telegram id/юзернеймы из тестовых чатов, использованных
      в этом чек-листе (id чатов и пользователей из шагов выше **не должны** попасть ни в один
      коммит — ни в тест, ни в фикстуру, ни в этот файл).
- [ ] Перезапуск бота (`docker compose restart bot` или эквивалент) после всех проверок —
      `alembic upgrade head` при старте контейнера должен пройти чисто на этой уже смигрированной
      базе (идемпотентность; см. `tests/integration/test_alembic_online_upgrade.py::test_upgrade_is_idempotent`
      для CI-эквивалента, но CI не проверяет реальный Dockerfile CMD).

## Готово, когда

- Все пункты выше отмечены.
- `pytest tests/unit tests/integration -q`, `ruff check src/ tests/`, `mypy src/` — зелёные.
- `alembic upgrade head` проходит на пустой базе (автотест
  `test_upgrade_head_succeeds_on_a_fresh_database` + ручной шаг 4 выше).
