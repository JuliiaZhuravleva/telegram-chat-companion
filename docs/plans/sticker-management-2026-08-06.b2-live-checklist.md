# Проверка стикера в личке админа — ручной чек-лист живой проверки (B-2)

> Дополняет автоматические тесты: `tests/unit/test_admin_sticker_handler.py`
> (`TestHandleAdminStickerCheck`, `TestHandleAdminStickerDmAnalyze`, `TestStickerDmCheckKeyboard`)
> и `tests/unit/test_admin_sticker_dm_router_order.py` (router-order regression: media.py's
> silent auto-learn must not fire for this path).
> Источник: `docs/plans/sticker-management-2026-08-06.md` §2 (B), ADR-0003
> (`docs/decisions/ADR-0003-sticker-analysis-transient-ui-state.md`).

Предусловие: доступ к живому боту в Telegram (админ-аккаунт из `admin_ids`, плюс второй,
НЕ-админский аккаунт для шага 2) и, по желанию, доступ к логам процесса бота для наблюдения за
строками `"Sticker duplicate detected..."`/загрузкой/анализом.

## 0. Что этот чек-лист НЕ проверяет

Юнит-тесты уже покрывают found/not-found текст, HTML-экранирование, кнопки, double-tap-подавление
`TelegramBadRequest`, обработку `download_telegram_file` ошибок и то, что `sticker_service.learn`
не вызывается на маршруте через реальный `main_router` (`test_admin_sticker_dm_router_order.py`).
Здесь — только то, что реально требует живого Telegram-клиента: настоящую доставку сообщений,
редактирование "в реальном времени", и поведение при параллельных аккаунтах/чатах.

## 1. Found / not-found в личке админа

- [ ] Из админ-аккаунта отправить боту в личку **уже известный** стикер (есть в каталоге,
      `SELECT * FROM sticker_knowledge WHERE file_unique_id = '...'`). Ожидается: бот отвечает
      реплаем на стикер с описанием/эмоцией/контекстами (тот же рендер, что в `adm_stk_view`),
      без кнопки "Проанализировать".
- [ ] Из того же аккаунта отправить боту стикер, которого **точно нет** в каталоге (свежий паблик-
      пак, который бот раньше не видел). Ожидается: реплай "Такого стикера ещё нет в базе." +
      кнопка "🔍 Проанализировать".

## 2. Analyze-кнопка + ADR-0003 (edit-in-place, ⏳ до блокирующего вызова)

- [ ] Нажать "🔍 Проанализировать" на прошлом шаге. Ожидается: сообщение с кнопкой сразу же
      меняется на "⏳ Анализирую…" **без кнопок** (визуально — до появления результата, не после),
      затем то же сообщение редактируется на итоговый текст (описание + кнопки Re-analyze/Clear)
      либо на "⚠️ Ошибка анализа: …" + кнопка Retry — **новое сообщение не отправляется**.
- [ ] Повторно отправить боту **тот же** стикер из шага 1 (not-found case) — теперь должен
      сработать found-путь (стикер уже выучен после Analyze).
- [ ] Двойной тап по "🔍 Проанализировать" (быстро дважды, если успеть до первого edit) — бот не
      должен упасть/показать ошибку Telegram-клиенту (double-tap подавляется в коде, но живой тап
      с реальной сетевой задержкой — единственный способ проверить настоящую гонку).

## 3. Admin+private scoping (граница, которую юнит-тесты не видят живьём)

- [ ] Тот же стикер из шага 1 отправить боту **от НЕ-админского аккаунта** в личку. Ожидается:
      никакого "не в базе"-реплая от DM-check-хендлера — сообщение уходит по обычному пути
      (`handlers/media.py`, молчаливое обучение группового типа); проверить в БД, что
      `sticker_knowledge` обновился обычным образом (без реплая с кнопкой).
- [ ] Отправить админом стикер **в группу** (не личку), где бот тоже есть. Ожидается: тот же
      обычный groupovый путь (`media.py`), НЕ DM-check — нет реплая "не в базе"/кнопки
      "Проанализировать" от имени DM-check-хендлера.

## 4. Регрессия: media.py больше не учит молча за DM-check-хендлером

- [ ] Отправить админом в личку **новый, никогда не виданный** стикер и НЕ нажимать
      "Проанализировать". Проверить в БД (`SELECT * FROM sticker_knowledge WHERE
      file_unique_id = '...'`): строки быть НЕ должно (или должна быть строка без
      `visual_description`, если где-то есть побочная запись) — то есть отправка стикера сама по
      себе не запускает анализ и не создаёт "тихую" запись в обход видимого UI-действия.
- [ ] (Опционально, если есть доступ к логам) Убедиться, что в логах процесса НЕТ следов
      `handle_sticker_message`/Vision-вызова для этого file_unique_id до нажатия кнопки —
      единственный лог должен быть от DM-check-хендлера (реплай "не в базе").
- [ ] Проверить, что при этом обычные (не DM-check) уведомления админам о новых стикерах в группах
      продолжают приходить как раньше (шаг 3, второй пункт, groupовый путь) — то есть регрессия
      специфична именно для DM-check маршрута, не сломала общий learn-путь.

## 5. Гигиена / regressions

- [ ] `git grep` по этому файлу и по `tests/` на реальные `file_id`/токены/chat_id, использованные
      при живой проверке — ничего из личных данных не должно попасть в коммит.
- [ ] `pytest tests/unit -q`, `ruff check src/ tests/`, `mypy src/` — зелёные (уже подтверждено
      автоматическими тестами B-2, здесь — финальная сверка перед закрытием чек-листа).

## Готово, когда

- Секции 1–2 подтверждают found/not-found/analyze и ADR-0003 edit-in-place живьём.
- Секция 3 подтверждает admin+private scoping (не-админ и group-чат оба уходят по обычному пути).
- Секция 4 подтверждает, что DM-check не создаёт побочного "тихого" обучения — ключевая регрессия,
  которую просил проверить B-1 (`last_update.note`).
- Секция 5 — гигиена подтверждена.
