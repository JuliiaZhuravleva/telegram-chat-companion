# Индикатор «бот печатает» — аудит и задача на внедрение

**Дата:** 2026-08-03
**Источник:** запрос владельца — «сейчас не всегда работает отображение статуса „бот печатает“.
Хотелось бы его внедрить везде, где это актуально».

## Что происходит сейчас (проверено по коду)

`send_chat_action` встречается в репозитории **ровно один раз** — в обработчике голосовых
сообщений и видеокружков ([media.py:81](../../src/bot/handlers/media.py#L81)). Больше нигде
индикатор не отправляется вообще. То есть «не всегда работает» — это мягкая формулировка:
он работает на одном сценарии из примерно десяти, и даже там — частично.

Второй, конкурирующий приём обратной связи — **сообщение-заглушка**: `/summary` шлёт
«⏳ Генерирую саммари...» и потом редактирует его ([commands.py:236](../../src/bot/handlers/commands.py#L236)).
В боте сейчас сосуществуют два разных языка обратной связи, и ни один не применяется
последовательно.

---

## I-1. Индикатор гаснет на длинных операциях (одноразовая отправка)

Telegram гасит chat action через **~5 секунд**. В [media.py:80-86](../../src/bot/handlers/media.py#L80-L86)
действие отправляется однократно, без повторения:

```python
typing_task = asyncio.create_task(
    bot.send_chat_action(message.chat.id, ChatAction.TYPING, message_thread_id=message_thread_id)
)
result = await voice_service.transcribe(...)
```

Транскрипция минутного голосового через Whisper регулярно занимает больше 5 секунд →
пользователь видит «печатает» пару секунд, потом тишину, потом внезапный ответ.
Это и есть основной наблюдаемый симптом «не всегда работает».

Нужен механизм, который **держит** действие всё время работы: повторная отправка
каждые ~4 секунды, пока операция не завершилась, с гарантированной остановкой
(в т.ч. при исключении).

## I-2. Основной путь ответа (текст) — индикатора нет вообще

Главный сценарий бота — ответ на упоминание/триггер/реплай — не показывает ничего.
[message.py:119](../../src/bot/handlers/message.py#L119) вызывает `pipeline.process(...)`,
внутри которого RAG-поиск, факты KB, сборка промпта и генерация LLM. Это секунды работы,
и всё это время в чате не происходит ничего.

Это самый заметный и самый частый пробел.

## I-3. Анализ фото — индикатора нет

[media.py:145](../../src/bot/handlers/media.py#L145): `image_service.analyze(image_data)` —
vision-вызов. Для фото с подписью следом идёт ещё и полный `pipeline.process`
([media.py:170](../../src/bot/handlers/media.py#L170)) — две длинные операции подряд, обе молча.

## I-4. Обучение на стикерах — индикатора нет

[media.py:315](../../src/bot/handlers/media.py#L315): `sticker_service.learn(...)` — тоже
vision-вызов. Здесь, впрочем, ответ пользователю не гарантирован (стикер-реплай
вероятностный), поэтому актуальность индикатора — предмет решения, а не данность.

## I-5. Команды с AI-вызовами — индикатора нет

- `/remember` — [commands.py:321](../../src/bot/handlers/commands.py#L321),
  `ai_router.generate_embedding(fact_text)`.
- `/summary` — использует заглушку вместо индикатора (см. I-7).
- Админ-мастер стикеров — [admin_sticker.py:138](../../src/bot/handlers/admin_sticker.py#L138),
  `merge_admin_description(...)`, LLM-вызов в личке с админом.

## I-6. Нет общего механизма — любая новая операция снова забудет индикатор

Корневая причина всего перечисленного: индикатор нигде не абстрагирован. Каждый
обработчик должен помнить о нём сам, и десять из одиннадцати — не вспомнили.
Пока нет разделяемого помощника (контекстный менеджер / декоратор / обёртка),
следующая длинная операция повторит ту же историю.

## I-7. Два несовместимых стиля обратной связи

`/summary` показывает текстовую заглушку, все остальные (в теории) — chat action.
Стоит определить правило: когда индикатор, когда заглушка, когда оба. Разумный
водораздел — по ожидаемой длительности (заглушка оправдана на десятках секунд,
где даже живой индикатор выглядит как зависание), но это решение владельца.

## I-8. Тип действия не всегда `typing`

Telegram поддерживает `upload_photo`, `choose_sticker`, `record_voice` и т.д.
Ответ стикером под `typing` — небольшая, но ложь. Где бот заведомо отвечает
стикером, честнее `choose_sticker`.

## I-9. Форумы: `message_thread_id` нужно передавать явно

Известная особенность проекта: `message.answer()` наследует `message_thread_id`
автоматически, а прямые методы бота (`bot.send_chat_action`) — **нет**. В существующем
вызове это учтено; любой общий помощник обязан протащить `message_thread_id`, иначе
в форум-супергруппах индикатор будет уходить в General вместо нужного топика.

## Открытые вопросы (нужно решение владельца)

1. **Случайные ответы (`TriggerType.RANDOM`).** Бот иногда вступает в разговор сам.
   Показывать ли «печатает» перед незапрошенной репликой? Индикатор перед случайным
   ответом выглядит навязчиво и вдобавок анонсирует ответ, который релевантность-гейт
   может ещё отменить (`result.should_respond == False`) — тогда «печатает» было ложью.
2. **Операции без гарантированного ответа** (обучение на стикере, анализ фото без
   подписи): бот работает, но может ничего не ответить. Показывать индикатор?
3. **Порог для заглушки vs индикатора** (I-7) — оставить `/summary` на заглушке или
   привести к общему виду?
4. **Настраиваемость:** делать ли индикатор per-chat переключателем (ещё одна колонка
   в `chat_settings` + слой в трёхслойном мердже) или это всегда-включённое поведение?

## Ограничения

- Public-репозиторий: в артефактах плана не должно быть реальных Telegram id.
- Трёхслойный конфиг: любая новая per-chat колонка — nullable, без DEFAULT (см. CLAUDE.md).
- Проверка: `pytest tests/ -v`, `ruff check .`, `mypy src/`.
- Локальный деплой + браузерная проверка в Telegram Web после изменения — индикатор
  по определению не проверяется юнит-тестами, только глазами в реальном чате.
